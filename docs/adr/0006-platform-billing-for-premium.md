# ADR-0006: Платформенный биллинг (Google Play Billing / Apple IAP) для премиума, без своего бэкенда

## Status

Accepted (2026-09-06, планируется к реализации в Фазе 6)

## Context

CLAUDE.md фиксирует автозаполнение форм как премиум-фичу («Premium-gate на
автозаполнение»), но не описывает, как технически принимается оплата.

При этом по ADR-0002 приложение не ведёт свою базу пользователей и не имеет
сервера: мы намеренно ничего не знаем о том, кто пользуется приложением.
Возникает вопрос: как продать платную функцию, если у продавца нет ни
покупателя в базе, ни способа принять платёж?

Классическая схема (свой бэкенд + аккаунт + подключение к платёжному
провайдеру типа Stripe) потребовала бы завести ровно то, от чего проект
осознанно отказался: сервер, хранение персональных/платёжных данных,
обязательства по их защите.

## Decision

Продажа премиума идёт через встроенный биллинг магазина приложений —
**Google Play Billing** на Android и **Apple In-App Purchase (StoreKit)**
на iOS. Приложение не заводит собственного аккаунта пользователя и не
обрабатывает платёжные данные напрямую.

Поток: пользователь инициирует покупку → нативный SDK магазина показывает
свой экран оплаты (карта и личность пользователя видит только магазин) →
магазин возвращает приложению подтверждение покупки → приложение
сохраняет флаг `premium: true` **локально**, в той же SQLite, что и
остальные данные (ADR-0002).

Сеть требуется только в момент самой покупки — инициируется явным
действием пользователя («Купить премиум»), контролируется SDK магазина,
а не собственным кодом приложения. Это узкое, осознанное исключение из
принципа «никакой сети в рантайме» (ADR-0002, ADR-0004): деньги физически
не могут перейти из рук в руки офлайн.

## Consequences

### Positive

- Не нужен свой бэкенд, аккаунт пользователя или обработка платёжных
  данных — вся ответственность и регулирование (PCI DSS и т.п.) остаются
  на стороне Google/Apple.
- Приложение по-прежнему не видит ни имени, ни email, ни карты
  пользователя — совместимо с «мы ничего не знаем о пользователе».
- «Restore purchases» — штатная функция обоих магазинов: если пользователь
  сменит телефон и войдёт в тот же Google/Apple аккаунт, статус премиума
  восстановится без всякой базы на нашей стороне. Частично компенсирует
  известный минус ADR-0002 (потеря устройства = потеря локальных данных) —
  но только для факта покупки, не для самих документов.
- Пользователю не нужно ничего регистрировать отдельно — оплата теми же
  реквизитами, что уже привязаны к магазину на телефоне.

### Negative

- **Проверка покупки полностью локальная**, без сервера, который бы
  сверял её напрямую с Google/Apple. Это слабее серверной проверки:
  теоретически более уязвимо к взлому/подмене ответа на взломанных
  устройствах (root/jailbreak), чем если бы легитимность каждой покупки
  подтверждал наш сервер. Для премиум-фичи с этим продуктом (не подписка
  на критичный сервис) риск принят осознанно; см. «Alternatives».
- Комиссия платформы (обычно 15-30%) с каждой покупки — в отличие от
  прямого приёма платежей.
- Обязательны обе платформенные библиотеки (`react-native-iap` либо
  раздельные обёртки Google Play Billing / StoreKit) — дополнительная
  нативная зависимость.
- Google Play и App Store требуют, чтобы **любая** цифровая функция внутри
  приложения продавалась именно через их биллинг — обойти платформенной
  комиссией нельзя.

### Neutral

- Юридический пункт из CLAUDE.md («перед платным тарифом проверить
  регулирование иммиграционного консультирования») не снимается этим
  решением — оно про то, как оплата технически проходит, а не про то,
  вправе ли продукт вообще продавать премиум-функцию в целевой юрисдикции.
- Подписки (если решим делать премиум подпиской, а не разовой покупкой)
  требуют периодической проверки статуса — тоже через тот же SDK, без
  своего сервера, но с сетевым обращением время от времени, а не только
  в момент первой покупки.

## Alternatives Considered

**Свой бэкенд + Stripe/аналог**
- Отвергнуто: требует сервера, аккаунта пользователя, хранения платёжных
  данных (или как минимум обмена с провайдером) — ровно то, от чего
  ADR-0002 отказывается ради приватности и простоты.
- В плюс шло: сильнее серверная проверка легитимности покупки, никакой
  комиссии платформы, возможна оплата вне магазинов приложений.

**Платный сам факт установки приложения (paid app), без премиум-фичи внутри**
- Отвергнуто: не даёт бесплатного пробного пути (Фаза 1-2 работают
  бесплатно), хуже для привлечения пользователей.

**Серверная проверка покупки (сервер дергает Google Play Developer API /
App Store Server API для валидации токена)**
- Отвергнуто на данном этапе: закрывает риск подделки покупки, но требует
  завести минимальный сервер только ради этой проверки — то есть
  частично отменяет ADR-0002 ради одной фичи. Кандидат на пересмотр
  отдельным ADR, если пиратство/подмена покупок станут ощутимой
  проблемой на практике.
