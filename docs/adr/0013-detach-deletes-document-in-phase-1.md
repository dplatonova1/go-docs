# ADR-0013: В Фазе 1 открепление файла — это полное удаление документа

## Status

Accepted (2026-09-16, Фаза 1 — прикрепление файлов)

**Временное решение на Фазу 1.** Заменяется в Фазе 2 вместе с экраном
библиотеки документов — см. «Deferred».

## Context

По [ADR-0010](./0010-shared-document-library.md) документ — сущность
библиотеки пользователя, а связь с пунктом чек-листа отдельна от него.
Открепление в этой модели означает «снять связь, документ оставить».

В Фазе 1 экрана библиотеки нет. Документ виден только там, где он
прикреплён, и попадает в приложение только через прикрепление к пункту,
поэтому каждый документ существует ровно в одном месте.

Если бы открепление снимало только связь, документ остался бы в базе, а
его зашифрованный файл — на диске. Пользователь не увидел бы ни того, ни
другого: экрана, где показываются документы без связей, не существует.
Такие файлы накапливались бы при каждом откреплении, занимали место и
оставались бы персональными данными, которые нельзя ни найти, ни
удалить. Это прямо противоречит [ADR-0002](./0002-local-first-storage.md)
и мотивировке ADR-0010, где дубликаты сканов названы проблемой.

Тот же инвариант уже зафиксирован в
[ADR-0012](./0012-delete-orphan-documents-with-application.md): «в Фазе 1
документов без связей не бывает».

## Decision

Открепление файла от пункта в Фазе 1 удаляет документ целиком:

1. связь в `checklist_item_documents`;
2. строку в `documents`;
3. зашифрованный файл на диске.

Первые два действия — в одной транзакции, файл удаляется после commit
(порядок и его обоснование — ADR-0012, раздел 3).

Документ удаляется, только если снимаемая связь была последней. Проверка
«остались ли другие связи» выполняется в той же транзакции: в Фазе 1
других связей не бывает, но полагаться на это в коде нельзя — иначе
переход к Фазе 2 придётся делать в двух местах.

Интерфейс называет действие своим именем: кнопка «Удалить», диалог
«Файл будет удалён без возможности восстановления». Слово «открепить»
не используется — оно обещает, что файл где-то останется, а он не
остаётся.

## Consequences

### Positive

- Невидимых файлов не возникает: всё, что лежит на диске, показано
  пользователю хотя бы в одном пункте чек-листа.
- Формулировка соответствует последствию, и необратимое действие не
  выглядит обратимым.
- Удаление файла — единственный способ убрать документ, и он доступен
  ровно там, где документ виден.

### Negative

- **Действие необратимо, а исходный файл мог быть удалён пользователем
  из источника.** Смягчается только текстом подтверждения.
- Поведение временное: в Фазе 2 те же кнопки должны работать иначе, и
  пользователи, привыкшие к Фазе 1, столкнутся с изменением.
- Проверка «остались ли другие связи» в Фазе 1 всегда даёт один и тот же
  ответ — это код, который не покрывается реальным сценарием, только
  тестом.

### Neutral

- Модель данных ADR-0010 не меняется: связь по-прежнему отдельна от
  документа, меняется только то, что делает интерфейс при откреплении.

## Deferred

**Фаза 2, вместе с экраном библиотеки документов:** открепление должно
снимать только связь, оставляя документ в библиотеке. Удаление документа
становится отдельным действием на экране библиотеки, с предупреждением о
том, в скольких заявках он используется (см. «Deferred» в ADR-0010).
Инвариант «документов без связей не бывает» на этом снимается — вместе с
таким же пунктом из ADR-0012. Оформляется новым ADR, заменяющим этот.

## Alternatives Considered

**Открепление снимает только связь (модель ADR-0010 без изменений)**

- Отвергнуто для Фазы 1: документ и его файл остались бы невидимыми и
  неудаляемыми — ровно та забытая копия персональных данных, против
  которой принимался ADR-0010.

**Не давать откреплять файлы до появления библиотеки**

- Отвергнуто: ошибиться файлом легко, особенно при выборе из галереи, а
  исправить ошибку было бы нельзя до Фазы 2.

**Мягкое удаление (пометка «удалён»)**

- Отвергнуто по тем же причинам, что в ADR-0010 и ADR-0012: фильтр в
  каждом запросе, а зашифрованный файл всё равно остаётся на диске.
