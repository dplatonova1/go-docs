# ADR-0014: Навигация — React Navigation (native-stack)

## Status

Accepted (2026-09-17, подготовка к Фазе 2). Структура стека дополнена
[ADR-0022](./0022-bottom-tabs.md): вкладки, у каждой свой native-stack.

## Context

В Фазе 1 библиотеки навигации не было сознательно
([`src/navigation/README.md`](../../src/navigation/README.md)): у
приложения одна заявка и два рабочих корневых состояния — «заявки нет» →
экран создания, «заявка есть» → её чек-лист. Переход между ними — смена
состояния, а не стек: возвращаться с чек-листа было некуда. Развилку
держал `RootNavigator` обычным `switch`.

С переходом на несколько заявок ([ADR-0015](./0015-multiple-applications-last-opened.md))
это перестаёт работать. Появляется экран списка заявок, и впервые
возникает переход, с которого **возвращаются**: список → чек-лист →
назад в список. Аппаратная кнопка «назад» на Android, жест «назад» на
iOS, кнопка в шапке и восстановление состояния после выгрузки процесса —
всё это в самодельной развилке пришлось бы писать и отлаживать вручную.

Тот же README называет условие: библиотека ставится, когда появится
первый экран, на который переходят и с которого возвращаются, а выбор
оформляется ADR. Это он.

## Decision

1. **React Navigation 7**: `@react-navigation/native` +
   `@react-navigation/native-stack`, с нативной зависимостью
   `react-native-screens`. `react-native-safe-area-context` в проекте уже
   есть.

2. **Именно native-stack, а не `@react-navigation/stack`.** JS-стек
   требует ещё `react-native-gesture-handler` и `react-native-reanimated`
   — три нативные библиотеки вместо одной, и каждая по правилу 3
   [ADR-0009](./0009-minimal-android-permissions.md) требует проверки
   разрешений, а перед публикацией — проверки 16 KB page size. Взамен
   native-stack отдаёт переходы и жесты платформы, что для приложения с
   простым стеком экранов ближе к ожиданиям пользователя.

3. **Структура стека:**

   ```
   RootStack (native-stack)
   ├── ApplicationList     — корень, без параметров
   ├── Checklist           — { applicationId }
   └── CreateApplication   — без параметров
   ```

4. **В параметрах маршрута — только идентификаторы**, не объекты
   предметной области. `Checklist` принимает `applicationId`, а заголовок
   и остальное подгружает сам. Параметры переживают выгрузку процесса и
   должны быть сериализуемы; кроме того, объект заявки в параметрах
   устарел бы после переименования.

5. **`RootStackParamList` типизирован**, `navigate` без `any` — правило
   из `src/navigation/README.md`.

6. **`linking` не настраивается.** Внешних ссылок, открывающих
   приложение с данными, быть не должно (там же).

7. **Заголовок — нативный**, цвета берутся из темы
   ([ADR-0011](./0011-styled-components.md)) через `screenOptions`.
   Собственные `Heading` с `accessibilityRole="header"` из экранов
   убираются: два заголовка подряд — шум для скринридера.

8. **Экраны остаются чистыми компонентами.** Данные маршрута загружает
   тонкая обёртка (`ChecklistRoute`), она же обрабатывает случай
   «заявка по этому id не существует». Структура папки компонента
   (`src/components/README.md`) не меняется, а тесты экранов не начинают
   зависеть от навигации.

## Consequences

### Positive

- Back-стек, жест «назад», кнопка в шапке и поведение аппаратной кнопки
  Android приходят из библиотеки, а не пишутся руками.
- Восстановление состояния после выгрузки процесса — штатная возможность
  `NavigationContainer`, и «последняя открытая заявка» ложится на неё
  естественно.
- `usePreventRemove` закрывает подтверждение о несохранённом черновике
  сразу для всех способов ухода с экрана — сейчас в
  `CreateApplicationScreen` вручную обрабатывается только аппаратная
  кнопка.
- Добавление экранов Фаз 2-5 (библиотека документов, сборка пакета,
  каталог форм) больше не требует расширять самодельную развилку.

### Negative

- **Новая нативная зависимость.** `react-native-screens` приносит
  `.so`-библиотеки: до публикации требуется проверка 16 KB page size на
  release-сборке (пункт уже есть в `CLAUDE.md`), а на iOS — `pod install`
  и проверка сборки.
- Тестам экранов нужен навигационный контекст или мок навигации;
  a11y-тесты, проверявшие внутриэкранный заголовок, переписываются под
  нативную шапку.
- Оформление шапки описывается не в `styles.ts` компонента, а в
  `screenOptions` навигатора — единственное место, где вид элемента живёт
  вне правила ADR-0011.
- Версии `@react-navigation/*` и `react-native-screens` связаны с версией
  React Native: обновление RN потребует согласованного обновления и их.

### Neutral

- Нативного кода, требующего разрешений, у `react-native-screens` нет:
  её `AndroidManifest.xml` пуст (проверено при установке, правило 3
  ADR-0009). Merged-манифест release-сборки проверяется отдельно, вместе
  с 16 KB page size.
- `enableScreens()` вручную не вызывается: в `react-native-screens` 4.x
  нативные экраны включены по умолчанию.

## Alternatives Considered

**Оставить самодельную развилку и добавить в неё экран списка**

- Отвергнуто: пришлось бы вручную писать стек, обработку аппаратной
  кнопки и восстановление состояния — ровно то, ради чего существует
  библиотека. Условие «ставим, когда появится возврат с экрана»
  выполнено.

**`@react-navigation/stack` (JS-стек)**

- Отвергнуто: тянет `react-native-gesture-handler` и
  `react-native-reanimated`. Больше нативных зависимостей — больше
  проверок разрешений и 16 KB page size, а выигрыш (настраиваемые
  анимации перехода) приложению не нужен.

**`react-native-navigation` (Wix)**

- Отвергнуто: нативные экраны дают лучшую производительность переходов,
  но интеграция тяжелее (правка `MainActivity`), экосистема и
  документация меньше, а выигрыш для трёх-пяти простых экранов
  незаметен.

**Expo Router**

- Неприменим: проект не на Expo ([ADR-0001](./0001-bare-react-native-new-architecture.md)).
