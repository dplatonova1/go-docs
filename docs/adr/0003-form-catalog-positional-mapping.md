# ADR-0003: Каталог форм — статичные шаблоны, fingerprint, маппинг по позиции

## Status

Accepted (2026-09-03, планируется к реализации в Фазе 3)

## Context

Официальные формы ведомств (первый кейс — сербская, уже разобрана) сделаны
в Word через **legacy form fields** (`w:ffData` / `FORMTEXT`), а не через
современные content controls.

Ключевое наблюдение из разбора реальных файлов: имена bookmark'ов у полей
не уникальны и не осмысленны — одно и то же `Text12` встречается на разных
по смыслу полях. Сопоставлять данные с полями по имени нельзя, это молча
приведёт к заполнению не тех ячеек.

Кроме того, пользователь скачивает файл сам, с сайта консульства. Имя файла
произвольное, а версия формы может отличаться от той, под которую строился
маппинг.

## Decision

Три отдельных решения, связанных общим замыслом:

1. **Маппинг строится один раз разработчиком** и хранится как статичный
   JSON-шаблон на форму, в бандле приложения. Каталог версионируется — на
   случай обновления формы ведомством.
2. **Поле определяется позицией в документе + текстом подписи перед
   полем**, не именем bookmark'а. Одно поле может соответствовать
   нескольким значениям сразу (номер паспорта + даты) — тогда заполняется
   одной строкой либо оставляется пользователю.
3. **Загруженный файл сопоставляется с шаблоном по структурному
   fingerprint** (количество и порядок полей, окружающий текст), не по
   имени файла.

PDF-формы (AcroForm) получают второй пайплайн на `@cantoo/pdf-lib` за тем же
интерфейсом (Фаза 5) — он нужен минимум для шенгенской визы, официально
распространяемой как PDF по Visa Code Annex I.

## Consequences

### Positive

- Устойчиво к переиспользованию имён полей — главной ловушке реальных форм.
- Устойчиво к переименованию файла пользователем.
- Рантайм остаётся простым и детерминированным: разбор шаблона, а не
  формы (см. ADR-0004).
- Обновление формы ведомством обнаруживается как несовпадение fingerprint,
  а не как тихое искажение данных.

### Negative

- Каждая новая форма — ручная работа разработчика. Каталог растёт линейно,
  не масштабируется «сам».
- Обновление формы ведомством ломает автозаполнение до выпуска новой
  версии приложения.
- Позиционный маппинг хрупок к правкам вёрстки внутри той же версии формы.

### Neutral

- Часть консульств выдают форму только через веб-портал, без скачиваемого
  файла — для них автозаполнение неприменимо в принципе, независимо от
  архитектуры.
- Тесты обязательны на реальных файлах-фикстурах, обезличенных.

## Alternatives Considered

**Маппинг по имени bookmark'а**
- Отвергнуто: имена не уникальны в реальных формах. Это и есть исходная
  причина всего решения.

**Маппинг по имени файла**
- Отвергнуто: пользователь переименовывает файлы; разные консульства
  раздают одну форму под разными именами.

**Content controls вместо legacy form fields**
- Отвергнуто: не наш выбор. Реальные формы сделаны на legacy fields,
  парсер обязан работать с тем, что есть.

**Распознавание формы «на лету» без каталога**
- Отвергнуто: см. ADR-0004 — требует LLM в рантайме, что несовместимо с
  офлайном и приватностью.
