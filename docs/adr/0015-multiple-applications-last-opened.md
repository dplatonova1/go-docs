# ADR-0015: Несколько заявок; активная — последняя открытая

## Status

Accepted (2026-09-17, подготовка к Фазе 2)

Снимает инвариант Фазы 1 «заявка ровно одна». Инварианты
[ADR-0012](./0012-delete-orphan-documents-with-application.md) и
[ADR-0013](./0013-detach-deletes-document-in-phase-1.md) при этом
остаются в силе — см. «Decision», пункт 5.

## Context

В Фазе 1 заявка была ровно одна. Это держалось не структурой данных, а
двумя местами в коде: `createApplication` отказывал, если заявка уже
есть, а `getActiveApplication` читал первую строку `applications` с
`LIMIT 1`. Схема при этом с самого начала допускала несколько заявок —
`checklist_items.application_id` есть в модели с миграции 1, а документы
по [ADR-0010](./0010-shared-document-library.md) изначально общие для
всех заявок.

Одна заявка — неправдоподобное ограничение: человек подаёт документы на
ВНЖ себе и членам семьи, подаёт в два ведомства, возвращается к прошлой
заявке через год. Именно ради этого сценария документы сделаны общей
библиотекой.

Как только заявок становится несколько, появляется вопрос, на который в
Фазе 1 отвечать было не нужно: **что открыть при запуске**. Вариантов
ровно два по смыслу — «ту, с которой человек работал в прошлый раз» или
«список, пусть выбирает». Первый вариант сохраняет нынешнее удобство
(приложение открывается сразу в работе), второй заставляет делать лишний
выбор при каждом запуске, хотя в подавляющем большинстве случаев человек
возвращается к той же заявке.

## Decision

1. **Ограничение «одна заявка» снимается.** Проверка
   `SELECT 1 FROM applications LIMIT 1` в `createApplication` и класс
   `ApplicationAlreadyExistsError` удаляются вместе с сообщением
   «Заявка уже создана. Перезапустите приложение, чтобы открыть её».

2. **«Активная заявка» = последняя открытая.** Хранится колонкой
   `applications.last_opened_at TEXT` (миграция 2). Отметка ставится
   после успешного открытия чек-листа.

3. **Сортировка списка заявок — по той же колонке:**
   `ORDER BY COALESCE(last_opened_at, created_at) DESC, id DESC`.
   `COALESCE` защитный: миграция заполняет колонку у существующих строк,
   а `createApplication` пишет её сразу, но код не полагается на «NULL
   тут не бывает». `id` — детерминированный разрыв ничьей.

4. **При запуске** стек навигации инициализируется как
   `[ApplicationList, Checklist{последняя открытая}]`: приложение
   открывается сразу в работе, но «назад» ведёт в список. Если заявок
   нет — только `ApplicationList` с пустым состоянием; отдельного
   корневого состояния «заявки нет» больше не существует.

5. **Инварианты ADR-0012 и ADR-0013 сохраняются.** Экрана библиотеки
   документов по-прежнему нет, поэтому документ без связей остаётся
   невидимым, и правила не меняются: удаление заявки удаляет документы,
   не прикреплённые больше нигде, а открепление файла означает его
   удаление. Меняется только то, что «больше нигде» теперь считается по
   нескольким реально существующим заявкам, а не по одной. Предикаты
   `ONLY_IN_APPLICATION` и `ALSO_IN_OTHER_APPLICATIONS` в `repository.ts`
   написаны так с самого начала и не правятся.

6. **Колонка `applications.status` не задействуется.** Она описывает
   состояние подачи документов (`in_progress`, `completed`, `archived`) и
   не имеет отношения к тому, какой экран открыть при запуске.

## Consequences

### Positive

- Сценарий, ради которого документы сделаны общей библиотекой (ADR-0010),
  становится достижимым: один паспорт закрывает пункты в заявках на всю
  семью.
- «Последняя открытая» не может указать на удалённую заявку: колонка
  живёт в строке `applications` и исчезает вместе с ней. Отдельное
  хранилище `last_application_id` потребовало бы ручной уборки и проверки
  «а существует ли ещё эта заявка».
- Та же колонка даёт порядок в списке заявок — «недавние сверху», без
  второго источника правды.
- Запуск приложения не меняется по ощущению: человек по-прежнему попадает
  сразу в свой чек-лист.

### Negative

- **Одна запись в БД при каждом открытии чек-листа.** База зашифрована
  (SQLCipher), запись идёт через журнал; на десятках строк это
  незаметно, но это запись там, где раньше было только чтение. Ошибка
  такого `UPDATE` глотается: потеря отметки «последняя открытая» не стоит
  сообщения пользователю и не должна ронять экран.
- Тексты подтверждений, написанные под одну заявку, становятся неверными
  и переписываются: сброс заявки больше не возвращает «к созданию
  заявки», а возвращает в список.
- Ветка «документы, прикреплённые также к другим заявкам, останутся» в
  диалоге сброса перестаёт быть теоретической — и впервые требует
  проверки на реальных данных, а не только тестом.
- Экран списка заявок — новый код и новые тесты там, где в Фазе 1 не было
  ничего.

### Neutral

- Миграции: `ALTER TABLE applications ADD COLUMN last_opened_at TEXT` и
  бэкфилл `UPDATE applications SET last_opened_at = updated_at`. Колонка
  объявлена nullable — SQLite не позволяет добавить `NOT NULL` без
  константного `DEFAULT`.
- Индекс по `last_opened_at` не заводится: заявок у человека единицы,
  сортировка десятка строк во временном B-tree неизмерима, а индекс —
  цена на каждой записи. Вернуться к вопросу, если появится сценарий с
  сотнями заявок.
- Схема данных не меняется ничем, кроме одной колонки: `checklist_items`,
  `documents` и `checklist_item_documents` уже спроектированы под
  несколько заявок.

## Deferred

**Вместе с экраном библиотеки документов (Фаза 2):** пересмотр ADR-0012 и
ADR-0013 — диалог удаления заявки должен предлагать «оставить в
библиотеке», открепление должно снимать только связь, а удаление
документа — предупреждать, в скольких заявках он используется. Инвариант
«документов без связей не бывает» снимается там же, а не здесь.

## Alternatives Considered

**«Активная» через `applications.status = 'in_progress'`**

- Отвергнуто: смешивает две разные вещи — состояние подачи документов и
  то, какой экран открыть при запуске. Заявок «в работе» может быть
  несколько одновременно, и вопрос «какую открыть» остался бы без
  ответа.

**Отдельная таблица `app_state` (ключ-значение) с `last_application_id`**

- Отвергнуто: ссылка на заявку вне строки заявки может протухнуть.
  Понадобились бы уборка при удалении и проверка существования при
  чтении — вместо колонки, которая исчезает сама.

**AsyncStorage или MMKV**

- Отвергнуто дважды: новая зависимость (по ADR-0009 — ещё одна проверка
  разрешений и 16 KB page size) и второе хранилище рядом с зашифрованной
  базой. «Какую заявку человек открывал последней» — тоже персональные
  данные, и им место внутри SQLCipher
  ([ADR-0002](./0002-local-first-storage.md)).

**Всегда открывать список заявок**

- Отвергнуто: у подавляющего большинства пользователей заявка одна или
  две, и лишний выбор при каждом запуске — плата за сценарий, который
  случается редко. Список остаётся в стеке под чек-листом и доступен
  кнопкой «назад».
