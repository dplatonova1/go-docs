# ADR-0020: В финальный пакет попадают только изображения и PDF

## Status

Accepted (2026-09-23, Фаза 2)

Фиксирует границу, которая до сих пор существовала как две отдельные
детали реализации: фильтр типов в пикере
([ADR-0018](./0018-deduplicate-documents-by-content-hash.md) описывает
соседнее решение того же файла) и ветка «не включено» в сборке
([ADR-0019](./0019-pdf-package-assembly.md), пункт 6).

## Context

Пакет — это PDF для печати. Значит, каждое вложение нужно превратить в
страницы. Технически приложение умеет ровно два способа:

- изображение (JPEG, PNG) — уменьшить, сжать и положить на страницу A4;
- PDF — вклеить его страницы как есть.

Всё остальное, что человек может принести из файлового менеджера, — docx,
odt, xlsx, heic, zip со сканами — страницами не становится без
конвертации.

Соблазн «поддержать docx» силён: ведомства часто выдают шаблоны именно в
нём, и пользователь резонно ожидает, что раз файл прикрепился, он
попадёт и в пакет. Отсюда и вопрос, который надо решить один раз и
записать.

Контекст, который сужает выбор:

- рантайм офлайновый и детерминированный
  ([ADR-0002](./0002-local-first-storage.md),
  [ADR-0004](./0004-no-llm-at-runtime.md)) — конвертировать «в облаке»
  нельзя;
- документы пользователя — паспорта и справки; любая новая библиотека,
  которая их разбирает, это новая поверхность атаки и новый повод для
  разрешений ([ADR-0009](./0009-minimal-android-permissions.md));
- пакет несут в ведомство. Молча подсунуть приблизительную копию
  документа хуже, чем не включить его вовсе.

## Decision

1. **Встраиваются только `image/jpeg`, `image/png` и `application/pdf`.**
   Тот же список — `ATTACHABLE_MIME_TYPES` — ограничивает пикер, так что
   в новых заявках других типов просто не появляется.

2. **Файл другого типа не конвертируется и не выбрасывается**, а
   попадает в реестр строкой «не включено — формат не поддерживается».
   Такие записи остаются от Фазы 1, когда пикер принимал что угодно.

3. **Сборка из-за них не срывается.** Пакет без одной страницы полезнее,
   чем отсутствие пакета; чего не хватает, видно в реестре на титульной
   странице.

4. **Пользователю не обещают большего.** Ни в пикере, ни в реестре нет
   формулировок вида «пока не поддерживается» — только факт: не
   включено, формат не поддерживается.

## Consequences

### Positive

- Поведение предсказуемо: что видно в чек-листе, то и окажется в PDF,
  либо будет названо в реестре.
- Ни одной библиотеки-конвертера в рантайме — ни в зависимостях, ни в
  поверхности атаки, ни в размере бандла.
- Сборка остаётся детерминированной: два пути обработки вместо пяти,
  каждый проверяется тестами на фикстурах.

### Negative

- **docx-шаблон ведомства в пакет не попадёт.** Пользователю придётся
  открыть его в стороннем приложении и сохранить как PDF. Для старых
  записей это разовая работа; для новых пикер не даст прикрепить такой
  файл вовсе.
- Пользователь может не понять, почему приложение «не умеет» формат,
  который открывается у него на телефоне. Смягчение — честный текст в
  реестре и в сообщении пикера («Прикрепить можно JPEG, PNG или PDF»).
- Решение придётся пересматривать, если окажется, что docx приносят
  часто: см. «Deferred».

### Neutral

- Ограничение не мешает Фазам 3-5: автозаполнение форм разбирает docx
  **как форму**, а не как вложение, и живёт отдельным пайплайном
  ([ADR-0003](./0003-form-catalog-positional-mapping.md)). Там разбор
  идёт по заранее проверенному шаблону, а не по произвольному файлу
  пользователя.

## Deferred

- **Считать, как часто пользователи упираются в это ограничение.**
  Отдельной телеметрии в приложении нет и не планируется (ADR-0002),
  поэтому сигналом будут обращения и отзывы.
- **Если докажет нужность — конвертация docx на стороне разработчика**,
  а не на устройстве: превращать в PDF шаблоны ведомств, которые мы и
  так разбираем для Фазы 3, и отдавать их уже готовыми. Это не отменяет
  ограничения на произвольные файлы пользователя.

## Alternatives Considered

**Извлекать из docx текст и печатать его**

- Отвергнуто. Технически это несложно (docx — zip с XML), но результат
  — не документ, а его пересказ: пропадают таблицы, печати, подписи,
  вёрстка бланка. В ведомство несут документ, а не его текст. Молчаливая
  подмена хуже честного «не включено», а объяснять в реестре «включено,
  но только текст» — значит предлагать пользователю самому оценивать
  пригодность того, чего он не видел.

**Полноценная конвертация: `mammoth` (docx → HTML) + html-to-pdf**

- Отвергнуто по совокупности:
  - **две тяжёлые зависимости в рантайме**, обе разбирают недоверенный
    файл пользователя. Для приложения, которое хранит паспорта, это
    заметное расширение поверхности атаки при нулевой выгоде для
    основного сценария;
  - **на устройстве нет движка рендеринга HTML в PDF.** Варианты —
    тащить WebView и печатать через него (новые разрешения, новая
    нативная часть, непредсказуемый результат на разных Android) либо
    JS-рендерер, который верстает приблизительно;
  - **результат непредсказуем**: `mammoth` намеренно отдаёт «чистый»
    HTML без сохранения оформления, дальше его верстает ещё один слой.
    Совпадение с исходным бланком — вопрос удачи, а проверить его
    пользователь сможет только в ведомстве;
  - **детерминированность рантайма** (ADR-0004) требует, чтобы одинаковый
    вход давал одинаковый выход. Цепочка из двух конвертеров этого не
    гарантирует между версиями библиотек.

**Не давать прикреплять неподдерживаемые файлы вообще, в том числе
старые**

- Отвергнуто: записи Фазы 1 уже существуют, и удалять их за
  пользователя — потеря данных. Они остаются в библиотеке, видны и
  удаляемы вручную ([ADR-0017](./0017-document-library-screen.md)).

**Вкладывать неподдерживаемый файл в PDF вложением (attachment)**

- Отвергнуто: пакет печатают. Вложение внутри PDF не окажется на бумаге
  и создаст ложное ощущение, что документ «в пакете».
