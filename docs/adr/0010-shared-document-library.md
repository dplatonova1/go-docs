# ADR-0010: Документы — общая библиотека пользователя, а не вложение в заявку

## Status

Accepted (2026-09-12, Фаза 0 — схема БД)

## Context

Один и тот же документ нужен в нескольких заявках. Человек подаёт на ВНЖ
в Сербии, через полгода — на шенгенскую визу, и скан паспорта требуется
обоим. То же с выпиской со счёта, справкой о несудимости, свидетельством
о браке: это не «документы заявки», а документы человека, которые заявки
у него запрашивают.

Отсюда следует, что в предметной области это две разные сущности:

- **пункт чек-листа** — требование («справка о несудимости»), пустое
  место, которое нужно закрыть;
- **документ** — конкретный файл, который у пользователя уже есть.

Одно закрывается другим, и связь между ними не обязана быть
единственной.

Дополнительное обстоятельство, специфичное для этого приложения: каждый
файл на диске хранится зашифрованным ([ADR-0002](./0002-local-first-storage.md)).
Дубликат скана — это не просто лишний мегабайт, а ещё одна копия
паспортных данных, которую придётся отдельно удалять и о которой легко
забыть.

## Decision

`documents` — самостоятельная таблица, не принадлежащая заявке. Связь с
пунктами чек-листа вынесена в отдельную таблицу
`checklist_item_documents` с составным первичным ключом
`(checklist_item_id, document_id)`.

```sql
CREATE TABLE checklist_item_documents (
  checklist_item_id TEXT NOT NULL REFERENCES checklist_items(id) ON DELETE CASCADE,
  document_id TEXT NOT NULL REFERENCES documents(id) ON DELETE CASCADE,
  attached_at TEXT NOT NULL,
  PRIMARY KEY (checklist_item_id, document_id)
);
```

Один документ может закрывать пункты в произвольном числе заявок.
`attached_at` относится к факту прикрепления в конкретном пункте и
отличается от `documents.created_at` — даты появления файла в библиотеке.

Из этого следует поведение, которое стоит проговорить: **удаление заявки
не удаляет документы**. Каскад по `checklist_item_id` снимает пункты
чек-листа и связи, но сами файлы остаются в библиотеке. Это правильно:
пользователь отказался от одной заявки, а не выбросил свой паспорт.

## Consequences

### Positive

- Документ загружается один раз. Повторное использование — штатный
  сценарий («прикрепить существующий»), а не обходной путь.
- Нет дубликатов зашифрованных файлов на диске, а значит и забытых копий
  персональных данных.
- Отказ от заявки не уничтожает библиотеку документов.
- Появляется возможность, которой при вложении в заявку не было бы:
  показать человеку, что у него уже собрано, до создания новой заявки.

### Negative

- **`ON DELETE CASCADE` на `document_id`: удаление документа из
  библиотеки молча убирает его из чек-листов всех заявок, где он был
  прикреплён.** Пользователь заходит навести порядок, удаляет «скан
  паспорта» — и в трёх заявках отмеченные пункты снова становятся
  пустыми, без предупреждения и без следа.

  Это противоречит принципу, на котором построен продукт в других
  местах: приложение не должно создавать у человека ложную картину
  состояния ([ADR-0005](./0005-mrz-with-manual-confirmation.md), там же
  формулировка «отмечено N из N»). Здесь оно создаёт обратную ложную
  картину — незаметную потерю уже подтверждённого прогресса.

  **Компромисс принят для MVP** по двум причинам: альтернатива
  (`RESTRICT`) без интерфейсной части превращается в необъяснимый отказ
  «документ удалить нельзя», а потеря ограничена связью — сам файл и сам
  пункт чек-листа остаются на месте, достаточно прикрепить заново.

  Занесено как известное ограничение; закрывается предупреждением в UI
  (см. «Deferred» ниже).

- Схема сложнее: три таблицы вместо двух, любой показ чек-листа требует
  join через связующую таблицу.

### Neutral

- Индексы подобраны под оба направления: составной первичный ключ
  закрывает выборку «какие документы прикреплены к пункту» (левый
  столбец), отдельный `idx_cid_document_id` — обратную, «где используется
  этот документ». Вторая понадобится как раз для предупреждения при
  удалении.
- На объёмах этого приложения (десятки заявок, сотни документов) разница
  в стоимости join против прямой связи неизмерима. Решение принято по
  соответствию предметной области, а не по производительности.

## Deferred

**Перед реализацией удаления документов (Фаза 1):** перед удалением
документа посчитать его связи и показать пользователю, где он
используется — «прикреплён в 3 заявках, удалить?». Запрос для этого уже
обеспечен индексом `idx_cid_document_id`. Пока такого предупреждения нет,
поведение остаётся тихим и описано выше как принятый недостаток.

## Alternatives Considered

**Документы 1:1 внутри заявки (`documents.application_id`)**

- Отвергнуто: не выдерживает основного сценария. Тот же скан паспорта
  пришлось бы загружать заново в каждую заявку, порождая копии
  персональных данных на диске. Хуже того, удаление заявки удаляло бы и
  паспорт — то есть обычная уборка стоила бы пользователю документов,
  которые он к этой заявке не привязывал.
- В плюс шло: схема проще на одну таблицу, никаких join, удаление
  документа затрагивает ровно одну заявку — то самое тихое поведение,
  которое сейчас записано в недостатки, там просто не возникло бы.

**Many-to-many, но `ON DELETE RESTRICT` на `document_id`**

- Отвергнуто для MVP: технически честнее — база не даст удалить
  используемый документ, — но без интерфейса это выглядит как
  немотивированный отказ. Правильная реализация требует UI, который
  объяснит, где документ используется, и предложит выбор. Кандидат на
  пересмотр вместе с пунктом из «Deferred».

**Мягкое удаление документов (`deleted_at`)**

- Отвергнуто: сохраняет связи, но добавляет фильтр «не удалённые» в
  каждый запрос к документам — цена, которую платят все запросы, ради
  проблемы, решаемой одним диалогом в интерфейсе. Плюс удалённые
  зашифрованные файлы продолжали бы лежать на диске, что для
  персональных данных нежелательно.
