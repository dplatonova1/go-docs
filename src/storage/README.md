# src/storage

Хранилище документов пользователя и ключ шифрования.

## Модули

| Файл | Назначение |
|---|---|
| [`fs.ts`](./fs.ts) | **Публичный API документов.** Шифрует при записи, расшифровывает при чтении |
| [`keychain.ts`](./keychain.ts) | Ключ шифрования: создание при первом запуске, чтение при последующих |
| [`crypto.ts`](./crypto.ts) | AES-256-GCM поверх `@noble/ciphers`; формат конверта |
| [`sandbox.ts`](./sandbox.ts) | Сырой доступ к песочнице **без шифрования** и проверка путей |
| [`base64.ts`](./base64.ts) | Кодирование base64 для нативного слоя (в React Native нет ни `btoa`, ни `Buffer`) |
| [`utf8.ts`](./utf8.ts) | Строгое декодирование UTF-8 (в Hermes нет `TextDecoder`, хотя в jest он есть) |
| [`errors.ts`](./errors.ts) | `StorageError` с кодом-дискриминантом |

## Главное правило

**Документы пользователя пишутся только через `fs.ts`.** `sandbox.ts` не
шифрует содержимое — он существует отдельно лишь потому, что
`keychain.ts` должен записать служебный файл-отметку, а зависеть от
зашифрованного `fs.ts` не может (тот сам просит у него ключ — получился бы
цикл).

Если документ записать через `sandbox.ts`, скан паспорта ляжет на диск
открытым текстом, и внешне всё будет выглядеть правильно.

## Публичный API файлов

`writeFile` / `readFile` / `deleteFile` / `fileExists` из `fs.ts`. Работают
с `Uint8Array`: документы бинарные, и байты — их честный тип. Кодирование
в base64, которого требует нативный слой, остаётся внутри `fs.ts` —
вызывающему о нём знать не нужно.

Сырой слой `sandbox.ts` использует те же глаголы с префиксом: `rawWrite`,
`rawRead`, `rawDelete`, `rawExists`.

## Как устроено шифрование

- Каждый файл шифруется AES-256-GCM тем же ключом, что и база данных
  ([ADR-0002](../../docs/adr/0002-local-first-storage.md)).
- GCM выбран потому, что это AEAD: он не только скрывает содержимое, но и
  обнаруживает подмену. Испорченный файл даст ошибку `file-corrupted`, а
  не мусор, принятый за документ.
- Nonce случайный и свой для каждой записи, в начале файла. Поэтому
  повторное сохранение одного и того же документа даёт разные байты — так
  и должно быть.
- Формат файла: `[1 байт версия][12 байт nonce][шифротекст + тег]`.
  Версия позволяет менять формат в будущем, не выдавая старые файлы за
  повреждённые.
- Ключ берётся из Keychain при каждой операции и не кэшируется в модуле.

## Ключ шифрования

- Генерируется системным генератором случайных чисел ОС
  (`crypto.getRandomValues` через `react-native-get-random-values`).
  Своей криптографии в проекте нет.
- Хранится в Keychain / Android Keystore, не мигрирует на другое
  устройство и в облачные бэкапы.
- Не попадает в БД, логи и аналитику. На пути записи ключа исходная
  ошибка намеренно не прикрепляется как `cause` — секрет является
  аргументом вызова и мог бы утечь в сообщение об ошибке.

### Обязательно при работе с ключом (ADR-0008)

У `react-native-keychain` есть незакрытый баг: на части Android-устройств
ранее сохранённый ключ перестаёт расшифровываться
([#802](https://github.com/oblador/react-native-keychain/issues/802)).
Для этого приложения это означает безвозвратную потерю всех документов —
бэкапа нет по ADR-0002.

Уже реализовано:

1. После записи ключ сразу читается обратно и сверяется.
2. Перед созданием нового ключа проверяется `hasGenericPassword()` — если
   запись есть, но не читается, создавать новый нельзя: это уничтожило бы
   доступ к документам.
3. Файл-отметка отличает «первый запуск» от «ключ пропал»: во втором
   случае новый ключ не создаётся, а бросается `encryption-key-lost`.

Все три поведения покрыты тестами в
[`__tests__/keychain.test.ts`](./__tests__/keychain.test.ts) — там же
разобрана вся таблица решений «ключ есть/нет × отметка есть/нет».

Ещё не сделано — см. «Отложенные обязательства» в
[CLAUDE.md](../../CLAUDE.md): выход из состояния «ключ потерян» (нужен UI)
и защита файла-отметки от удаления.
